# Interaction Analysis

ACMM keeps general requirement/dimension analysis separate from experiment-specific interaction
questions. Core provides reusable interaction-analysis machinery, but it does not register a
historical experiment ID or infer a factorial design from scenario names.

An Experiment Package that needs interaction analysis should supply an explicit design describing
its factors, cell mapping, estimands, blocking/repetition structure, and desired outputs. Packages
without such a scientific design receive only the general analysis layers.

## Estimands

For a complete 2 x 2 binary-factor design, one useful estimand is a risk-difference
difference-in-differences:

```text
[p(A1, B1) - p(A1, B0)] - [p(A0, B1) - p(A0, B0)]
```

The analysis should also report relevant simple effects so an interaction is not interpreted in
isolation. If a requirement does not have opportunities in all required cells, Core must not invent
outcomes; the interaction is marked not estimable while available cell rates/effects remain
descriptive.

## Uncertainty

When repeated conditions are interleaved within a common repetition/block, bootstrap resampling
should preserve that block structure. Missing planned slots are not imputed. Degenerate observed
outcomes may retain a point estimate while avoiding misleading zero-width nonparametric intervals.

The exact resampling unit and estimability rules belong to the package's declared design rather than
to an experiment-name registry in Core.

## Outputs

Reusable R/Python tooling may write normalized interaction tables, standalone figures, and an
interaction workbook under an execution's analysis output. Statistical figures should preferably be
generated by the same R path that constructs the analysis population and factors; Excel-native
charts remain an acceptable presentation fallback.

The general `analysis_report.xlsx` remains focused on Core analysis. Experiment-specific interaction
artifacts are separate outputs owned by the package's analysis design.
